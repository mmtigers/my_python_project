# 仕様書ドリフト同期 (spec-drift-sync)

## これは何のためのスキルか

`docs/specifications/` には、`MY_HOME_SYSTEM/*.py`・`DDD/*.py`・`family-quest/src/**/*.{ts,tsx,js,jsx}` の
ソースファイル1つにつきMarkdown仕様書が1つ対応する、という規約がこのリポジトリにはある
（例外: `全体設計書.md`、各ディレクトリの`README.md`。対象外: `tests/`、`__init__.py`、`migrations/`、`.d.ts`）。

`.github/scripts/check_spec_drift.py` によるCIチェックが存在するが、**常に非ブロッキング**
（exit code 0固定）であり、コメントを残すだけでPRをマージ不可にはしない。つまり「気づいても放置される」
ことが構造的に起きやすい。実際に2026-08の一斉監査では98件中44件がドリフトしていた。

このスキルは、そのチェックが検知した内容を実際に埋める（仕様書を書く/直す）ところまでを担う。
CIスクリプト自身は検知しかしないので、対応する作業はこのスキルが行う。

## 全体の流れ

1. **検知する**: 変更したソースファイルと、対応する仕様書のズレを機械的に洗い出す。
2. **書く/直す**: 検知された各ファイルについて、仕様書を新規作成または該当箇所のみ更新する。
3. **検証する**: 再度チェックを走らせて検知がゼロになったことを確認する。

### 1. 検知する

作業ブランチと比較対象(通常はデフォルトブランチ)のコミットSHAを確認し、次を実行する。

```bash
cd MY_HOME_SYSTEM/../  # リポジトリルート
python3 .github/scripts/check_spec_drift.py pr --base <base-sha> --head <head-sha>
```

`--base`/`--head` は `git merge-base origin/main HEAD` や `git rev-parse HEAD` などで取得する。
まだリモートに存在しないローカル作業中のブランチの場合は、`--head` に作業ツリーの最新コミット
（未コミットの変更があれば先にコミットしておく）を渡す。

出力は3種類に分類される。それぞれの対応方針:

| 検知区分 | 意味 | 対応 |
| --- | --- | --- |
| 📄 仕様書が見つからないファイル | 新規/未文書化のソース | 仕様書を新規作成する（下記フォーマット参照） |
| ⚠️ ドリフトの可能性 | ソースは変更されたのに対応する仕様書がPR内で更新されていない | 仕様書の該当セクションを実際の差分に合わせて更新する |
| 🕸️ 孤立ドキュメント（ソース削除時） | ソースファイルが削除されたのに仕様書がそのまま | 仕様書を「廃止notice」に書き換える（後述） |

対応先パスの規則（スクリプトが機械的に使っているものと同じ）:
- `MY_HOME_SYSTEM/**/name.py` や `DDD/name.py` → フラットに `docs/specifications/<dir>/name.md`
  （サブディレクトリ構造は畳まれる。例: `MY_HOME_SYSTEM/services/quest_service.py` →
  `docs/specifications/MY_HOME_SYSTEM/quest_service.md`）
- `family-quest/src/**` → 基本的に `src/` 配下の構造をそのままミラー
  （例: `family-quest/src/hooks/useGameData.ts` → `docs/specifications/family-quest/src/hooks/useGameData.md`）。
  ただし `src` 直下の `App.tsx`/`main.tsx` だけは `src/` を省いた歴史的例外パス
  （`docs/specifications/family-quest/App.md`）にある。

### 2. 書く/直す

**必ず `docs/specifications/MY_HOME_SYSTEM/notification_service.md` を実例として読んでから書くこと。**
このリポジトリの仕様書は自由形式ではなく、`docs/specifications/README.md` に定義された固定の
10セクション構成に厳密に従う:

1. 解析メタ情報（対象ファイル・言語・解析対象・推測補完の有無の表）
   + 関連ドキュメント（相互参照する他の仕様書へのリンクと、参照理由の一言）
2. ファイルの概要
3. 外部依存関係（インポート一覧の表、ブラックボックスとなる外部要素の表）
4. 主要要素の定義（関数/クラス/エンドポイントごとに、役割・引数/リクエスト・戻り値/レスポンス・
   副作用・エラーハンドリングの5項目を記述）
5. 処理フロー図（主要関数のmermaid `flowchart`）
6. 依存関係図（mermaid `graph`）
7. 次のステップ（関連して読むべきファイルの提案、優先度付き）
8. 保守上の注意点
9. 不明事項一覧
10. 自己検証結果（チェックリスト）

このフォーマットで最も重要な規約は、**4章のすべての記述に「根拠: [種別](行番号 / 抜粋)」を
必ず付けること**、そして**ソースコードのみを根拠にし、推測や補完を書かないこと**である
（1章の「推測・補完」欄は基本的に「一切なし」にする）。分からないことは9章の不明事項に
正直に書く。これはCLAUDE.mdの規約ではなく仕様書自体の自己検証ルール（10章）なので、
新規作成時はもちろん、既存仕様書の一部だけを更新するときも、更新した箇所については
このルールを守ること。

作業の性質ごとの書き方:

- **新規作成**（📄検知）: 対象ソースファイルを実際に開き、上記10セクションをすべて埋める。
  `notification_service.md` の粒度・書式（表の列、「根拠」の書き方、mermaidの記法）をそのまま
  踏襲する。
- **部分更新**（⚠️検知）: ソースの差分（`git diff <base> <head> -- <該当ファイル>`）を確認し、
  実際に変わった関数・引数・フロー・依存関係に対応する章だけを直す。無関係な章まで書き直す
  必要はない。ただし、変更によって8章（保守上の注意点）や9章（不明事項）の内容が古くなって
  いないかは毎回確認する。
- **削除**（🕸️検知）: 仕様書の内容を消し去るのではなく、冒頭に「このファイルは `<date>` 時点で
  ソース (`<path>`) が削除されたため廃止されました」のような廃止noticeを追記する形にする
  （既存の解析内容は履歴として残す）。

複数ファイルが検知された場合、1ファイルずつ順に処理してよい。並行して手を広げすぎると
「根拠」の付け忘れなど品質が落ちやすいので、1ファイルごとに10章のチェックリストを満たしてから
次に進む。

### 3. 検証する

書き終えたら、コミット後の状態で再度同じコマンドを実行し、扱った範囲について検知がゼロに
なっていることを確認する。

```bash
python3 .github/scripts/check_spec_drift.py pr --base <base-sha> --head <head-sha>
```

まだ検知が残っている場合（対応漏れ、パス規則の勘違いなど）は該当ファイルを追加で直す。

## 注意点

- このチェックは非ブロッキングなので、フォーマットのみの変更やコメント修正など、仕様書の
  実質的な更新が不要なケースまで無理に仕様書を書き換える必要はない。判断に迷う場合は
  「ソースの外部から見た挙動・シグネチャ・依存関係が変わったか」を基準にする。
- `full` サブコマンド（`check_spec_drift.py full`）はPR差分に関係なくリポジトリ全体を監査する
  週次バッチ用のモードで、コミット日時ベースの比較のため通常のPR作業では使わない。ただし
  「このリポジトリ全体の仕様書ドリフトを棚卸ししたい」という依頼のときはこちらを使う。
- 仕様書自体のコメント・文言は日本語で書く（`docs/specifications/` 配下は全て日本語）。
