## 仕様書の規約

- ソースファイル1つにつきMarkdown仕様書1つが対応します(例外: 本ファイルおよび各ディレクトリの`README.md`、`全体設計書.md`)。
- 各仕様書は「解析メタ情報」「ファイルの概要」「外部依存関係」「主要要素の定義」「処理フロー図」「依存関係図」「次のステップ」「保守上の注意点」「不明事項一覧」「自己検証結果」の10セクションで構成される固定フォーマットです。
- 単体解析の限界を補うため、各仕様書には「関連ドキュメント」(関連する他仕様書へのリンク)と、不明事項が他ドキュメントの解析結果から判明した場合の「相互参照による補足情報」を追加しています(詳細は[全体設計書.md 6-5](./全体設計書.md)参照)。
- ソースと仕様書の対応関係は `.github/scripts/check_spec_drift.py` によって自動監査されています(PR差分チェック・週次全体監査)。

### 解析基準コミット (Issue #287)

先頭の「1. 解析メタ情報」テーブルに `解析基準コミット` 行を追加できます。値は、その仕様書の内容がどのコミット時点のソースを根拠に書かれた(＝最後に人手/Claudeによって検証・更新された)かを示す短縮SHA(`git rev-parse --short`と同じ7桁、`git log -1 --format=%h -- <該当ファイル>` で取得できる、そのMarkdownファイル自身の最終更新コミット)です。空欄のまま(行自体が無い)仕様書は、このIssue以降まだ検証されておらず、`check_spec_drift.py` のドリフト検知結果以外に鮮度を判断する材料が無いことを意味します — 仕様書を新規作成・実質的な内容変更をする際は、その時点の`git rev-parse --short HEAD`（または対応するソースファイルを実際に読み直して確認した基準コミット）をこの行に記入してください。この行は「ソースファイル側がそれ以降に変更されていないか」までは保証しません(それは`check_spec_drift.py`の役割です)。あくまで「この解析内容はこのコミット時点で人手/Claudeにより確認された」という検証時点の記録です。

### 「(修正済み)」注記の書式 (Issue #287)

「保守上の注意点」等で、かつてのバグが後続コミットで修正済みであることに触れる箇条書きは、`* **[修正済み] <見出し>**: <説明>` の形式に統一します(見出し中の「（修正済み）」「（バグ修正済み）」「修正済み: 」といった位置・表記ゆれのある注記は、見出しの直前に置く`[修正済み]`タグ1種類に正規化する)。Issue番号や内部管理番号(例: `M-6-4`)などの参照情報は注記タグとは別に見出し内に残してください。単に文中で過去形として「〜するよう修正済み」と述べているだけの記述(独立した注記ではなく通常の説明文)はこの対象外です。
