# システム全体設計書 (Integrated System Architecture)

## 1. システム全体概要

本システムは、家庭環境の自動化・ロギング、ゲーミフィケーションを通じたタスク管理、および外部データの自動収集とコンテンツ生成を統合管理する複合型プラットフォームです。全体は大きく3つの独立したサブシステムで構成され、互いに連携しながら自律的かつ非同期に稼働しています。

### 1.1. サブシステム構成

1. **MY_HOME_SYSTEM (バックエンドコア)**
   * **役割**: IoT機器の制御、環境データの収集・分析、各種API・Webhookの統合ルーティング。
   * **技術要素**: Python, FastAPI, Raspberry Pi (推測), 各種外部API (SwitchBot, Nature Remo, LINE等)。

2. **Family Quest (フロントエンドUI)**
   * **役割**: 家族のタスク（クエスト）をRPG風に管理し、モチベーションを向上させるクライアントアプリケーション。
   * **技術要素**: React, TypeScript, Vite。

3. **DDD (データ処理バッチ・コンテンツ生成)**
   * **役割**: 特定プロジェクト（Secret Wallet等）に向けたデータ自動収集、プロンプト生成、および動画・音声のバッチダウンロード処理。
   * **技術要素**: Python, yt-dlp, Discord API等。

## 2. サブシステムA: MY_HOME_SYSTEM (バックエンドコア)

すべてのハードウェア制御、データロギング、外部サービス連携を担うシステムの心臓部です。

### 2.1. コンポーネント一覧と役割

#### A. コアサーバー・ルーティング機構
* **`unified_server.py` / `system_router.py`**:
  各種APIリクエストの受け口となり、処理を各ドメインサービスへ委譲する統合エントリーポイント。
* **`webhook_router.py`**:
  外部システムからのPush通知（Webhook）を受け取り、適切なハンドラへルーティングする。
* **`bounty_router.py`**:
  報酬システムに関するAPIルーティング。
* **`camera_router.py`**:
  カメラのライブ配信（HLS）・録画セグメントの一覧取得や配信APIを提供する（`services/camera_service.py` に処理を委譲）。パストラバーサル対策として、配信ファイルパスを `base_dir` 配下に限定するバリデーションを行う。

#### B. ハードウェア・IoT制御モジュール
* **`switchbot_service.py`**:
  SwitchBotデバイス（プラグ、ボット等）の制御およびステータス（電源状態、消費電力等）の取得。
* **`nature_remo_monitor.py`**:
  Nature Remoを介した家電制御と、温度・湿度等の環境センサーデータの監視。
* **`camera_monitor.py`**:
  ネットワークカメラの稼働監視およびスナップショット取得。
* **`camera_digest_service.py`**:
  カメラの録画・スナップショットから要約（ダイジェスト）コンテンツを生成する（`camera_router.py`とは別系統で、監視・要約寄りの役割）。
* **`tv_lock_monitor.py`**:
  TVの稼働時間を監視し、規定時間を超えた場合のロック制御を行う。
* **`connect_speaker.py`**:
  スマートスピーカー等への音声出力・通知連携。

#### C. 外部サービス・通知連携
* **`line_logic.py` / `line_handler.py`**:
  LINE Messaging APIを利用した双方向通信。ユーザーからのメッセージ解析、メニュー表示、システムからの通知送信を行う。
* **`google_photos_service.py`**:
  Google Photos APIと連携し、特定アルバムへの写真アップロードや取得を行う。
* **`weather_service.py`**:
  外部の天気APIから気象情報を取得し、システム内の判断材料（例：雨の日の特定タスク発火など）に利用する。

#### D. AI・分析エンジン
* **`ai_service.py`**:
  LLMを活用した推論・テキスト生成の共通インターフェース。
* **`log_analyzer.py`**:
  蓄積された各種ログ（センサー、タスク消化、システムログ）のパターンを分析する。
* **`weekly_analyze_report.py`**:
  週次で家庭内の状況（健全性、タスク消化率など）をAIで要約し、レポートとして出力（LINE等へ送信）する。

#### E. クエストバックエンド (Family Quest用API)
* **`quest_router.py` / `quest_service.py` / `game_logic.py`**:
  フロントエンド(Family Quest)からのリクエストを処理。ユーザーのレベル計算、経験値(コイン)の付与・消費、ボス討伐状況の更新、報酬インベントリの管理を計算し、データベース(DB)へ永続化する。

#### F. インフラ・監視タスク (フェイルソフト機構)
* **`server_watchdog.py`**:
  サーバープロセスの死活監視。異常検知時の再起動処理など。
* **`nas_monitor.py`**:
  NASの接続状態、ディスク容量の監視。枯渇前の事前アラート発報。
* **`memory_monitor.py`**:
  システムのメモリ使用量を監視し、OOM (Out of Memory) を未然に防ぐ。
* **`cron_reporter.py`**:
  定期実行ジョブ（Cron）の実行結果をまとめ、管理者にレポートする。

### 2.2. 主要なデータフロー
* **センサー監視フロー**:
  `nature_remo_monitor` / `switchbot` ➡ `sensor_service` ➡ `database` に時系列保存 ➡ `weekly_analyze_report` が集計 ➡ LINEへ送信。
* **WebHook通知フロー**:
  外部システムからのPush ➡ `webhook_router` ➡ 内容解析 ➡ `line_handler` を通じてユーザーへ通知。

## 3. サブシステムB: Family Quest (ゲーミフィケーションUI)

MY_HOME_SYSTEMのクエストAPIと連携し、タスクをRPG風に管理するReactベースのSPA（Single Page Application）です。

### 3.1. コンポーネント構成と役割

#### A. アプリケーション基盤
* **`App.tsx`**:
  ルートコンポーネント。全体の表示モード(`viewMode`)、アクティブなタブ(`activeTab`)、選択中のユーザー(`currentUserIdx`)をStateとして一元管理し、各画面・モーダルをマウントする。
* **`main.tsx`**:
  Reactツリーのレンダリングおよび、React Query (QueryClient) などのプロバイダ設定を行うエントリーポイント。
* **`@/types` (推測)**:
  `User`, `Quest`, `Item` などのTypeScript型定義を管理。

#### B. クエスト・タスク管理機能
* **`QuestList.tsx` / `ApprovalList.tsx`**:
  日常のタスク（クエスト）を一覧表示。通常・特別・無限クエストを分類してレンダリングする。
* **`useQuestStatus` (カスタムフック)**:
  クエストの状態（未完了、申請中、完了）を管理・判定するロジック。

#### C. ユーザー・ファミリー状態管理
* **`UserStatusCard.tsx`**:
  選択中ユーザーの現在のレベル、HP、経験値プログレスバーを表示する。
* **`FamilyMileageCard.tsx`**:
  家族全体で共有するポイント（マイレージ）の状態を可視化する。
* **`BossCard.tsx`**:
  現在出現しているボスモンスターの情報（HP、属性など）と、攻撃ボタン（クエスト完了連携）を表示する。
* **`WeeklyTrends.tsx`**:
  直近のクエスト消化傾向や活動履歴をグラフ等で表示する。

#### D. 報酬・ショップ機能
* **`EquipmentShop.tsx`**:
  獲得したコインを消費して装備品を購入するUI。
* **`RewardList.tsx`**:
  設定されたご褒美（リアルな報酬等）の一覧と交換用UI。
* **`InventoryList.tsx`**:
  現在所持しているアイテムや装備品の確認画面。
  * ※これら3コンポーネントは、タブ切り替え役だった `ShopContainer.tsx` が削除された後（fix(family-quest): add build config, fix critical/high findings）、`App.tsx` が直接マウントしている。

#### E. 共通UI・演出エフェクト
* **`Modal.tsx` / `LevelUpModal.tsx` / `MessageModal.tsx`**:
  汎用的なモーダルダイアログ群。
* **`ConfirmModal`**:
  独立したコンポーネントファイルではなく、`App.tsx` 内にローカル定義された確認ダイアログ（`App.tsx` 61-110行付近）。クエスト完了・却下・購入確認など、アプリ内の `confirm()`/`alert()` はすべてこの `ConfirmModal` と `MessageModal` に置き換え済み。
* **`BattleEffect.tsx`**:
  クエスト完了（ボス攻撃時）の視覚的な演出（斬撃エフェクトなど）を描画する。
* **`useSound` (カスタムフック)**:
  承認音、レベルアップ音、攻撃音などのSE（サウンドエフェクト）再生ロジック。

#### F. カメラ機能（追加サブシステム）
* **`features/camera/components/{LiveView,RecordView,CameraDashboard}.tsx`**:
  バックエンドの `camera_router.py` が配信するHLSライブ映像・録画セグメントを表示するUI群。
* **`components/ui/HlsPlayer.tsx`**:
  上記カメラ機能が利用するHLS再生プレイヤーコンポーネント。
  * ※この一群はドキュメント作成時点（2026年6月）より後に追加された機能だが、個別の仕様書（`docs/specifications/family-quest/src/features/camera/`、`.../components/ui/HlsPlayer.md`）を新規作成済み。

### 3.2. データフロー・状態管理
* **クエスト完了フロー**:
  1. ユーザーが `QuestList` でクエスト完了をタップ。
  2. `App.tsx` の `executeConfirm()` が発火。
  3. `useGameData.completeQuest()` 経由でバックエンド(`quest_router.py`)へAPIリクエスト。
  4. (成功時) `bossEffect` ステートが更新され、`BattleEffect` が描画される。
  5. APIから最新のユーザー・ボス状態を再フェッチし、UIを更新。

## 4. サブシステムC: DDD (データ処理バッチ・コンテンツ生成)

情報収集および特定のコンテンツ展開（Secret Wallet等）を支える独立したバッチスクリプト群です。

### 4.1. コンポーネント一覧と役割
* **`batch_download_discord.py`**:
  設定時間帯（既定02:00〜06:00）に、複数のURLリストファイルから動画をNAS等へバッチダウンロードする。`DownloadStrategy`抽象基底クラスを軸に `UniversalYtDlpStrategy`（yt-dlp経由）と `ScrapingStrategy`（missav等の個別サイトスクレイピング＋JS展開）を切り替える戦略パターンを採用。`fcntl.flock`によるロックファイル(`.batch_download_discord.lock`)で多重起動を防止する。
* **`extract_youtube_urls.py`**:
  指定されたYouTubeチャンネルやプレイリストからURLリストを抽出する。
* **`file_utils.py`**:
  `batch_download_discord.py` / `extract_youtube_urls.py` で重複していたファイル名サニタイズ処理を共通化したユーティリティ。
* **`newface_monitor.py`**:
  特定サイトの新人紹介ページを定期巡回し、新規キャストの追加を検知してDiscordへ通知する。
* **`split_prompts.py`**:
  長大なプロンプトやシナリオテキストを論理的なチャンクに分割する。

  ※旧版で存在した `bot_cookies.txt` / `split_results/` / `data/known_casts.json` は現在のリポジトリ上には存在しない（削除済みまたは実行時生成物としてリポジトリ管理外）。

### 4.2. データ処理フロー
* **自動ダウンロードフロー**:
  1. 定期実行（Cron等）で起動。
  2. 対象リスト (`list/` 内のテキストファイル等) を読み込み。
  3. `nas_monitor` の情報やローカル容量をチェック。
  4. `yt-dlp` 等のライブラリを用いてNAS上の指定ディレクトリへ保存。
  5. 実行結果を `history.txt` に追記。

## 5. システム間連携とデータフロー (統合ビュー)

3つのサブシステムは、主に**データベース（DB）**、**NAS（ストレージ）**、および**REST API**を介して連携しています。

1. **日常のロギングとゲーミフィケーションサイクル**
   * `[Family Quest (UI)]` ➡ クエスト完了API ➡ `[MY_HOME_SYSTEM (Backend)]`
   * バックエンドがDBを更新（ユーザー経験値UP、ボスのHP減少）。
   * 同時に、`[IoTデバイス]` ➡ 環境データをDBへ随時保存。
   * 週末に `weekly_analyze_report.py` がこれらを総合して分析し、家族の活動サマリーをLINEへ通知。

2. **ストレージリソースの協調**
   * `[DDD (Batch)]` は大量のメディアデータをNASへダウンロード。
   * `[MY_HOME_SYSTEM]` の `nas_monitor.py` がNAS容量を監視し、DDDの活動によって容量が逼迫した場合はアラートを発報、または一時的にバッチを停止させる。

## 6. 保守・拡張に向けた指針 (推奨事項)

コード構成の解析に基づき、今後の保守性・安定性を高めるためのポイントを抽出しました。

1. **APIインターフェースの型同期 (TypeScript ↔ FastAPI)**
   * `useGameData.ts` の `familyMileage` 用 `useQuery` ジェネリクスや `ApproveResponse.bossEffect` など、`any` 型が残っている箇所が一部あります（大部分は解消済み）。FastAPIのOpenAPI (Swagger) スキーマからTypeScriptの型定義を自動生成（`openapi-typescript` 等を利用）することで、残る箇所も含めてバックエンドとフロントエンド間のデータ構造の不一致によるランタイムエラーを防ぐことができます。

2. **ブラウザ標準APIの脱却 (Family Quest) — 対応済み**
   * 以前は一部のコンポーネントで `window.confirm()` / `alert()` が使用されていましたが、`ApprovalList.tsx` / `InventoryList.tsx` / `GuildBoard.tsx` / `AdminDashboard.tsx` / `AvatarUploader.tsx` 等で `Modal` / `MessageModal` ベースの確認・通知UIへの置き換えが完了しています（各コンポーネントのソース中に `★変更` コメントで記録あり）。

3. **バッチ処理の冪等性（べきとうせい）確保 (DDD)**
   * ダウンロードバッチ（`batch_download_discord.py`等）は `fcntl.flock` によるロックファイルで多重起動は防止済みですが、途中でプロセスがクラッシュした場合に「どこまでダウンロードが完了したか」を正確に再開できる仕組み（DBでのステータス管理、またはファイルのハッシュチェック等）は未強化のままです。深夜帯の無人稼働の信頼性向上のため、引き続き推奨事項とします。

4. **未文書化ファイルの解消 — 対応済み**
   * 品質監査で発見した、ドキュメント作成時点（2026年6月）より後に追加され未文書化だった以下のファイル群について、個別の仕様書を新規作成しました。
     * Family Quest: `docs/specifications/family-quest/src/features/camera/components/{LiveView,RecordView,CameraDashboard}.md`, `.../features/camera/types/index.md`, `.../components/ui/HlsPlayer.md`
     * MY_HOME_SYSTEM: `dashboard.md`, `post_boot_health_check.md`, `quest_data.md`, `reset_game.md`, `train_service.md`, `camera_router.md`, `camera_service.md`
     * DDD: `file_utils.md`, `newface_monitor.md`

5. **仕様書の相互参照による充実化 — 対応済み**
   * 各仕様書は単体のソースファイルのみを対象に機械的に解析されたため、「不明事項一覧」に「他ファイルを見ないと判断できない」項目が多数残っていました。DDD/MY_HOME_SYSTEM/family-questの全115件の仕様書（本ファイルを除く）について、インポート関係・呼び出し関係・フロントエンド⇔バックエンドAPI対応などを手がかりに相互参照を行い、以下の2種類のセクションを追加しました。
     * `## 関連ドキュメント`（解析メタ情報の直後）: 内部モジュール、呼び出し元/呼び出し先、対応するバックエンドAPIやフロントエンドコンポーネントなど、関連する他の仕様書へのリンクと関係性の一言説明。
     * `## 相互参照による補足情報`（不明事項一覧の直後、該当項目が解決できた場合のみ）: 元の「不明事項一覧」は変更せず保持したまま、関連する他の仕様書の解析結果に基づき判明した情報を、あくまで「他ドキュメントからの補足」である旨を明記した上で追記（推測・断定的な行番号根拠の捏造は禁止し、関連仕様書側も未確認の場合は解決扱いにしない方針を徹底）。
   * 既存の各仕様書のセクション番号・本文・自己検証結果は一切変更していません。
